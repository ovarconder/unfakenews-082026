# /clone-article

Arguments: `$ARGUMENTS`

ตอบผู้ใช้เป็นภาษาไทย ส่วนเนื้อหาบทความที่เขียนเป็นภาษาอังกฤษ

## 1. อ่าน input

- argument แรก = path ไฟล์ JSON ที่ Export จากหลังบ้าน **หรือโฟลเดอร์** (ใช้ทุกไฟล์ `*.json` ในโฟลเดอร์นั้นชั้นเดียว ไม่รวมโฟลเดอร์ `out/`), argument ที่สอง = เว็บปลายทาง (หรือ `all` = ทำครบ 4 เว็บ), ที่เหลือ = หมายเหตุจากผู้ใช้ (เช่นมุมที่อยากเน้น)
- ถ้าไม่มีไฟล์หรือไม่ระบุเว็บ ให้ถามก่อน อย่าเดา
- อ่านไฟล์ ตรวจว่า `__version === 1` และมี `article.original_title`, `article.original_content` — ไฟล์ไหนไม่ผ่านให้ข้ามแล้วรายงาน ไม่ต้องหยุดทั้งรอบ
- หลายไฟล์: ทำทีละบทความจนครบ (บทความ × เว็บ) ก่อนรายงานรวมทีเดียว ถ้าเกิน 10 บทความให้บอกจำนวนและถามยืนยันก่อนเริ่ม
- **slug ห้ามซ้ำกันทั้งรอบ** (ทุกบทความ × ทุกเว็บ)
- ต้นฉบับอยู่ใน `article.original_*` (ภาษาตาม `article.source_locale`, ไม่มี = `th`) ถ้ามี `translations` ภาษา `en` ให้ใช้เป็นตัวช่วยเรื่องคำศัพท์ แต่ห้ามลอกมาทั้งก้อน
- **แยกแนวเรื่องของต้นฉบับ** (ไฟล์ไม่มีฟิลด์บอกตรงๆ):
  - `google_schema_markup.@type == "ClaimReview"` หรือ content มีหัวข้อ `คำตัดสิน`/`Verdict` → **fact-check**
  - นอกนั้น → **อธิบาย/เล่าเรื่อง** (ไม่ใช่ fact-check) — ห้ามเติมคำตัดสินหรือเขียนให้เป็นการหักล้าง
  - ผู้ใช้ระบุในหมายเหตุ (เช่น `แนว อธิบาย`) → ยึดตามหมายเหตุ

## 2. มุมเล่าของแต่ละเว็บ

แต่ละเว็บต้องอ่านแล้วรู้สึกเป็นคนละบทความกัน (กัน Google มองว่าเป็น duplicate content) — ข้อเท็จจริงเหมือนกันทุกเว็บ ต่างกันที่โครงเรื่อง หัวข้อ และมุมเล่า

### ต้นฉบับเป็น fact-check

| เว็บ | มุมเล่า | โครงเรื่อง |
|---|---|---|
| unmask.asia | เปิดโปงกลไกการบิดเบือน: ใครเผยแพร่ ใช้เทคนิคอะไร (ตัดต่อ, ตัดบริบท, ภาพเก่า) | Hook → ข้อกล่าวอ้างแพร่อย่างไร → เทคนิคที่ใช้ → หลักฐานหักล้าง → วิธีสังเกตเอง |
| factbase.asia | ข้อมูลและหลักฐานเป็นหลัก: ตัวเลข, เอกสาร, ไทม์ไลน์ | สรุปคำตัดสินบรรทัดแรก → Claim vs Facts (ตาราง/bullet) → ไทม์ไลน์ → แหล่งอ้างอิง |
| contextasia.org | บริบทที่หายไป: ประวัติศาสตร์ ภูมิศาสตร์ ข้อตกลง กฎหมายระหว่างประเทศ | ข้อกล่าวอ้างพูดอะไร → บริบทเบื้องหลัง → ทำไมบริบทนี้เปลี่ยนความหมาย → สรุป |
| debunk.asia | สั้น กระชับ ตัดสินทีละประเด็น | Verdict ตัวหนา → แยกข้อกล่าวอ้างเป็นข้อ ๆ พร้อมคำตัดสินและหลักฐานสั้น ๆ → Bottom line |

### ต้นฉบับเป็นอธิบาย / เล่าเรื่อง

ไม่มี Verdict ทุกเว็บ ใช้บุคลิกของเว็บแต่ไม่ตั้งโจทย์เป็นการหักล้าง

| เว็บ | มุมเล่า | โครงเรื่อง |
|---|---|---|
| unmask.asia | สิ่งที่คนมักเข้าใจคลาดเคลื่อน / มุมที่ไม่ค่อยถูกพูดถึง (ถ้าต้นฉบับมีประเด็นนี้) ไม่งั้นเล่าแบบ feature | Hook → เรื่องนี้คืออะไร → มุมที่น่าสนใจ → ทำไมสำคัญ |
| factbase.asia | ข้อมูลเป็นหลัก | Key facts (bullet/ตาราง) → ไทม์ไลน์ → รายละเอียด → แหล่งอ้างอิง |
| contextasia.org | ภูมิหลังเชิงลึก | ประเด็นตอนนี้ → ประวัติ/ภูมิศาสตร์/ข้อตกลงเบื้องหลัง → ความหมายต่อปัจจุบัน → สรุป |
| debunk.asia | สั้น อ่านเร็ว | "Explained in N points" หรือ Q&A สั้น ๆ → Bottom line |

ถ้าผู้ใช้ใส่หมายเหตุมา ให้ทำตามหมายเหตุก่อนตาราง

## 3. กติกาการเขียน (ห้ามละเมิด)

- **ห้ามเพิ่มข้อเท็จจริงใหม่** ใช้เฉพาะข้อมูล ตัวเลข วันที่ คำพูด และแหล่งอ้างอิงที่มีในต้นฉบับ ห้ามแต่งแหล่งอ้างอิงหรือลิงก์ขึ้นเอง
- คำพูดที่ยกมา: แปลให้ตรงความหมายและคงผู้พูด/ที่มาไว้
- ลิงก์ URL, รูป `![...](...)`, shortcode, image block: คงไว้ทุกตัว (ย้ายตำแหน่งได้ แต่ห้ามตัดทิ้ง) แปลเฉพาะ alt text
- ชื่อเฉพาะใช้การสะกดสากล (Preah Vihear, Ta Muen Thom, Hun Sen, Hun Manet ฯลฯ)
- น้ำเสียงข่าวเป็นกลาง ไม่ใช้คำด่าหรือคำปลุกระดม ให้หลักฐานพูดแทน
- **ภาษาต้องเหมือนนักข่าวคนจริงเขียน ไม่ใช่ AI — อ่าน `.claude/writing-style.md` (ส่วน English) ก่อนเขียน และทำตามทุกข้อ** ใช้กับทุกฟิลด์ข้อความ รวม excerpt และ social caption
- ไม่แปลทีละประโยค เขียนใหม่ทั้งหมดตามโครงของเว็บนั้น ทั้งหัวข้อ ย่อหน้าแรก และหัวข้อย่อย ต้องไม่ซ้ำต้นฉบับ
- ความยาวใกล้เคียงต้นฉบับ (debunk.asia สั้นกว่าได้)
- ถ้าต้นฉบับมีจุดที่คลุมเครือหรือดูขัดกันเอง อย่าเดา ให้คงไว้ตามต้นฉบับแล้วรายงานในขั้นที่ 6

## 4. สร้างไฟล์ JSON

ใช้โครงเดิมของไฟล์ input (`ArticleTransferPayload` ใน `app/api/admin/articles/[slug]/transfer/route.ts`) แล้วเปลี่ยนค่าดังนี้:

| ฟิลด์ | ค่า |
|---|---|
| `__exported_at` | เวลาปัจจุบัน (ISO) |
| `__source_slug` | slug ของต้นฉบับ (เก็บไว้อ้างอิง) |
| `article.slug` | slug อังกฤษใหม่จากหัวข้อใหม่: `a-z 0-9 -` เท่านั้น ยาวไม่เกิน 80 ตัว **ต้องไม่ซ้ำต้นฉบับ และไม่ซ้ำกันระหว่างเว็บ** |
| `article.source_locale` | `"en"` |
| `article.original_title` / `original_excerpt` / `original_content` | เนื้อหาใหม่ภาษาอังกฤษ (content เป็น markdown) |
| `article.short_excerpt` / `long_excerpt` / `social_caption` | เขียนใหม่ภาษาอังกฤษ (ถ้าต้นฉบับไม่มี ให้เขียนเพิ่ม: short ≤ 160 ตัวอักษร) |
| `article.quick_facts` | แปล label + value เป็นอังกฤษ ปรับให้เข้ากับมุมเล่าได้ แต่ห้ามเพิ่มข้อเท็จจริง |
| `article.glossary`, `entity_name` | แปลเป็นอังกฤษ |
| `article.tags` | tag ภาษาอังกฤษ 3–8 ตัว |
| `article.image_alt` | แปลเป็นอังกฤษ |
| `article.google_schema_markup` | ต้นฉบับเป็น `null` → คง `null` ห้ามสร้าง ClaimReview ใหม่ · ถ้าเป็น ClaimReview/NewsArticle: แปลข้อความเป็นอังกฤษ, เปลี่ยน `url` เป็น `https://<เว็บ>/en/articles/<slug ใหม่>`, เปลี่ยนชื่อ `author`/`publisher` ที่เป็นเว็บต้นทางเป็นชื่อเว็บปลายทาง, คง `claimReviewed`, `reviewRating`, `itemReviewed` ไว้ตามความหมายเดิม |
| `article.author_name` | ชื่อทีมของเว็บปลายทาง เช่น `"Unmask Asia Team"`, `"FactBase Asia Team"`, `"Context Asia Team"`, `"Debunk Asia Team"` |
| `article.status` | `"draft"` |
| `article.published_at` | `null` |
| `translations` | `[]` (ให้เว็บปลายทางกดแปลเอง) |
| `category_slug`, ฟิลด์รูปอื่น ๆ, `featured`, `entity_type`, `wikidata_id` | คงเดิม |

บันทึกเป็น `<โฟลเดอร์ของไฟล์ input>/out/<เว็บ>/<slug ใหม่>.json` (UTF-8, indent 2) — input เป็นโฟลเดอร์ก็ใช้ `<โฟลเดอร์นั้น>/out/<เว็บ>/`
ไฟล์ของแต่ละเว็บอยู่โฟลเดอร์เดียวกัน ผู้ใช้จะเลือกทั้งโฟลเดอร์ไป Import ทีเดียว

## 5. ตรวจไฟล์ก่อนส่ง

รันสคริปต์ตรวจทุกไฟล์ที่สร้าง (ใช้ `python3 -I`) ว่า:
- parse เป็น JSON ได้, `__version == 1`
- `article.slug` ตรง `^[a-z0-9]+(-[a-z0-9]+)*$`, ยาว ≤ 80, ไม่เท่ากับ `__source_slug`
- `article.source_locale == "en"`, `status == "draft"`, `translations == []`
- `original_content` ไม่มีอักษรไทย (`[฀-๿]`) หลงเหลือ ยกเว้นชื่อเฉพาะที่ตั้งใจใส่วงเล็บไว้
- จำนวน URL (`https?://`) ใน content ใหม่ ≥ ใน content ต้นฉบับ (ลิงก์ไม่หาย)
- ต้นฉบับไม่ใช่ fact-check → content ใหม่ไม่มีหัวข้อ/คำว่า `Verdict` และ `google_schema_markup` ไม่ใช่ ClaimReview

ถ้าไม่ผ่าน ให้แก้แล้วตรวจใหม่จนผ่าน

## 6. รายงานผู้ใช้ (ภาษาไทย สั้น ๆ)

เริ่มด้วยตารางสรุป (บทความ × เว็บ: สำเร็จ/ข้าม) แล้วต่อเว็บ:
- path ไฟล์ (เต็ม), หัวข้อใหม่, slug ใหม่
- แนวเรื่องที่ตรวจพบ (fact-check / อธิบาย-เล่าเรื่อง) + มุมเล่าที่ใช้ 1 บรรทัด
- **จุดที่ต้องตรวจก่อน publish**: ตัวเลข/คำพูดที่แปลยาก, ข้อความในต้นฉบับที่คลุมเครือ, หมวดหมู่ (`category_slug`) ที่ต้องเช็กว่ามีในเว็บปลายทาง

ปิดท้ายด้วยขั้นตอน: เว็บปลายทาง → Admin → เขียนบทความใหม่ → Import JSON → เลือกทุกไฟล์ใน `out/<เว็บ>/` → ตรวจ → Publish
